# 玩法接入示例

[战斗文档导航](../战斗系统与DSL.md) · [战斗世界与帧循环](战斗世界与帧循环.md)

本页基于使用此框架的项目代码提炼玩法接入示例，展示当前 Lcc 尚未包含的 Gameplay 实现如何组织。代码经过机制提炼，省略项目资源、数值与业务专用功能；不是直接移植的完整玩法。未运行原项目或验证 Lcc 中的编译结果。

## 1. 两份工程的关系

| 项目 | 源码中的情况 |
| --- | --- |
| 当前 Lcc | 保留内核与基础节点，Gameplay 配置注册器为空，未包含具体玩法世界 |
| 参考项目 | 具有 ECGameWorld、CreationInfo、玩法初始化、配置容器和技能/Buff 等具体实现 |

参考项目使用 `HotUpdate.CoreGame` 等命名空间，Lcc 使用 `LccHotfix`。以下片段保留可辨认的类与方法名，但省去 using 和完整类型外壳，不应整段复制后假定能够编译。

## 2. 从 CreationInfo 注入服务

参考项目的 `ECGameWorldCreationInfo` 继承 `BattleKernelCreationInfo`，在构造时装配时间、计时器、DSL、伤害、目标查询、技能策略、表现及日志等服务。具体 Gameplay 服务类留在玩法层。

```text
局外模式/关卡准备
  → 构造 Gameplay CreationInfo
  → 注入 Kernel 定义的接口与策略实现
  → 提供玩家、关卡与模式 ID
  → 创建玩法世界
```

这说明“内核可以被多个玩法使用”的实际落点是服务注入：内核调用伤害或技能策略接口，项目则选择自己的实现，而不是把关卡、角色或模式分支塞进内核系统。

迁移到 Lcc 时应逐项对照 [BattleKernelCreationInfo](../../Assets/Hotfix/GameLogic/CoreGame/BattleKernel/World/Core/BattleKernelCreationInfo.cs)。参考项目里的全局服务入口和业务类型在 Lcc 中并不存在，不能只更换命名空间。

## 3. 初始化顺序决定模式能否创建

示例对应的世界子类这样扩展初始化系统：

```csharp
protected override void AddInitializeSystems(ECSystems systems)
{
    base.AddInitializeSystems(systems);
    systems.Add(new SysGameplayInitialize(this));
}
```

`SysGameplayInitialize` 是参考项目提供的玩法系统。它准备共享上下文和模式逻辑创建参数，核心赋值顺序可概括为：

```csharp
var genInfo = service.NewGenInfo<CustomLogicGenInfo>();
genInfo.ConfigContainerName = LogicContainerKey.LogicConfigs_GameMode;
genInfo.LogicConfigID = creationInfo.ModeLogicID;
genInfo.PreEnv = modeEnvironment;
creationInfo.GameModeGenInfo = genInfo;
creationInfo.ModeLogicService = modeLogicService;
```

这里 `service`、`creationInfo`、`modeEnvironment` 和 `modeLogicService` 表示已经准备好的服务、创建信息、模式黑板及玩法模式服务。参考项目还写入玩家、关卡、场景等信息，并注入死亡处理和击退策略。

世界装配时对应的初始化顺序为：

```text
SysKernelInitialize
  → SysGameplayInitialize
  → SysKernelGameModeInitialize
  → 其他初始化系统
```

模式系统在后续初始化中需要读取 `GameModeGenInfo` 和 `ModeLogicService`，所以不能等到游戏已经进入帧循环才补它们。这里的先后来自系统注册及初始化接口，不是靠手动等待若干帧。

## 4. 配置注册发生在创建逻辑之前

示例注册器一次装配模式、实体状态机、技能、子物体、关卡、Buff、AI 等容器。保留关键部分的注册片段如下：

```csharp
service.AddConfigContainer(new LogicConfigs_GameMode(LogicContainerKey.LogicConfigs_GameMode));
service.AddConfigContainer(new LogicConfigs_EntityFSM(LogicContainerKey.LogicConfigs_EntityFSM));
service.AddConfigContainer(new LogicConfigs_Skill(LogicContainerKey.LogicConfigs_Skill));
service.AddConfigContainer(new LogicConfigs_Subobject(LogicContainerKey.LogicConfigs_Subobject));
service.AddConfigContainer(new LogicConfigs_Buff(LogicContainerKey.LogicConfigs_Buff));
```

这些 `LogicConfigs_*` 是参考项目的配置类，Lcc 当前没有对应的完整实现。可复用的是“容器职责 → 正确根类型 → 配置注册 → 创建请求”的组织方式。

| 容器 | 参考项目中的组织方式 |
| --- | --- |
| Skill | 根类型是 SkillLogic，按角色或功能拆为多个 partial 文件 |
| Subobject | 根类型是 SubobjectLogic，组织移动、碰撞与命中配置 |
| Buff | 通过 BuffCfg 创建 BuffLogic，配置持续时间和合并规则 |
| GameMode | 持有模式行为，使用玩法初始化准备的上下文 |

注册接口的依据见 Lcc 的 [CustomLogicManager](../../Assets/Hotfix/Framework/CorePackage/CustomLogic/CustomLogicManager.cs)，容器名与 ID 的查找规则见 [DSL 配置与执行](DSL配置与执行.md)。

## 5. 扩展系统时保留内核阶段

参考项目通过覆写各 `Add*Systems` 方法追加玩法能力，例如：

| 阶段 | 内核执行后的玩法扩展 |
| --- | --- |
| Rule | 交互物触发，使用已经刷新的 Bounds |
| Move | NavMeshAgent 同步等位移相关处理 |
| Battle | 弹药恢复、近战减速等项目逻辑 |
| SyncView | 英雄移动动画、UI 位置和弹药表现同步 |
| Late | 血条、补给、飘字等收尾 |

其共同形式是先调用 `base.Add*Systems(systems)`，再添加需要的玩法系统。追加的位置表达数据依赖，而不是按文件目录就近放置。

这也不代表所有追加系统每帧都执行：仍要检查它们实现的是 Initialize、Execute、FixedUpdate 还是其他接口。尤其碰撞入口与普通逻辑更新不能混写成一个同步执行序列。

## 6. 关闭世界时先处理玩法资源

参考项目的玩法初始化系统同时实现 TearDown，负责清理击退委托、效果调度器以及玩法持有的屏幕效果等资源，并调用相关效果和对象池服务释放资源。

值得沿用的是“谁注入、谁持有，就明确由谁在关闭时解绑或归还”。DSL 实例回收不能替代全局效果服务、对象池或世界层委托的清理；反过来，清空对象池也不能替代停止活动逻辑。

迁移时按实际所有权设计释放，不应把参考项目的全局 `ClearAll` 等调用直接加入一个可能共享服务的世界。

## 7. 与 Lcc 对照时从哪里补起

1. 先准备模式容器与模式服务，再补 Gameplay CreationInfo 和世界子类。
2. 把玩家/关卡上下文和模式创建参数放进玩法初始化阶段。
3. 注册首局必需的容器，再从最简单的技能、子物体和 Buff 建立闭环。
4. 分别验证世界更新、固定碰撞更新、模式初始化与停止释放。

参考源码落点均位于参考工程的 `BattleGameplay`：`World/Core/ECGameWorld.cs`、`World/Core/ECGameWorldCreationInfo.cs`、`World/Systems/Initialize/SysGameplayInitialize.cs` 和 `LogicDsl/Authoring/LogicCfgContainerRegister_Gameplay.cs`。这些是来源标识，当前 Lcc 没有对应文件，因此不创建失效源码链接。

真实技能与 DOT 的配置实践见 [技能与 Buff 示例](技能与Buff示例.md)。
